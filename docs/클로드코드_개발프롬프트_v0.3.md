## 프롬프트 본문

너는 이 저장소에서 **새한프라텍 「주간 생산계획 수립 지원 툴」 프로토타입**을 개발한다.
요구사항 원본은 `docs/새한프라텍_주간생산계획수립지원툴_요구사항정의서_v0.2.pdf`이다. 코드를 쓰기 전에 이 문서를 끝까지 읽어라. 특히 4장(기능 요구사항), 5장(데이터 정의·계산식), 6장(화면 구성), 9장(확정할 사항)을 꼼꼼히 봐라.

### 1. 배경 (요약)
- 고객사는 용기(PET 프리폼·병, PE) 제조사다. 오창 공장의 주간 생산계획은 생산지원팀장 1인이 엑셀로 수기 작성한다.
- 이 툴은 **자동 계획 툴이 아니라 의사결정 지원 툴**이다. 계획을 데이터로 입력·저장하고, 예상 생산량·수급 부족·제약 위반을 계산해 경고하고, 씨벌크(SEA BULK) 원료 사일로 재고를 6주 앞까지 예측한다. 최종 확정은 사람이 한다.
- 계획 기간은 **이번 주 목요일부터 2주 뒤 목요일까지 15일**이다. 근무는 3조 12시간 주야 교대, 연중무휴다.

### 2. 이번 프로토타입 범위
- **대상 설비:** 오창 1공장 1-Stage **PET 1~18호기**만. 데이터 모델은 2-Stage(사출 P·블로우 S), PE, 2공장을 나중에 추가할 수 있게 `공정유형`·`공장` 필드를 처음부터 둔다.
- **구현:** 요구사항의 **P0 전부(FR-01~10, FR-12)와 P1 전부(FR-11, FR-13~17)**.
- **구현하지 않음:** P2(FR-18, 19), 10장 2단계 후보(초안 추천, 변경 영향 분석, 2-Stage 연동), 인원배치(다른 부서 과제), ERP(MOLD) 실제 연동, 자동 발주.

### 3. 기술 조건
- **배포: Vercel. 데이터베이스: Supabase(PostgreSQL).** 이 조합에 맞춰 아래 스택을 쓴다.
  - Next.js(App Router) + TypeScript, Vercel 배포. 서버 로직은 Route Handler / Server Action으로.
  - Supabase: PostgreSQL, Supabase Auth(이메일 로그인), Row Level Security로 역할(작성/조회/관리) 권한 구분. 스키마는 `supabase/migrations/`의 SQL 마이그레이션으로 관리한다.
  - 엑셀 입출력: SheetJS(xlsx) 또는 ExcelJS. 업로드 파일 파싱은 서버에서.
  - 테스트: Vitest(계산 엔진), Playwright(핵심 화면 스모크 테스트).
  - 계산 엔진은 프레임워크와 분리된 순수 TypeScript 모듈(`lib/engine/`)로 만든다. 브라우저에서도 돌아가게 해서 간트 수정 시 1초 안에 재계산한다.
- **보안·데이터 (NFR-01 관련):** 요구사항 원문은 사내 처리 전제다. 프로토타입 단계는 Vercel·Supabase에 **가상 데이터 또는 고객이 허락한 마스킹 데이터만** 올린다. 실제 원본 데이터(`data/samples/`)는 커밋·업로드하지 말고 `.gitignore` 처리한다. 운영 전환 시 사내 호스팅으로 옮길 수 있도록 Supabase 전용 기능 의존을 최소화하고(표준 PostgreSQL + 인증 계층 분리), README에 이전 방법을 적어 둔다.
- 키·비밀값은 코드에 넣지 않는다. `SUPABASE_SERVICE_ROLE_KEY`는 서버에서만 쓰고, `.env.example`에 변수 이름만 적는다.
- 사용자는 IT 초급이고 엑셀에 익숙하다. 화면은 **엑셀 계획표처럼 호기가 행, 날짜가 열**인 모양을 유지한다. 한국어 UI. 기준 해상도는 사무실 PC(1920×1080), 최소 1366px.

### 3-1. UI 디자인
- **폰트: Pretendard.** `pretendard` npm 패키지 또는 `next/font/local`로 셀프 호스팅한다(외부 CDN 금지). 숫자는 `font-variant-numeric: tabular-nums`로 자리를 맞춘다.
- **분위기: 고객사 홈페이지 https://www.splatech.com/ 에 맞춘다.** 개발 시작 전에 사이트를 직접 열어(브라우저 또는 웹 조회) 주조색, 보조색, 여백, 사진·아이콘 톤을 확인하고 디자인 토큰으로 정리해 계획 단계에서 보여줘라. 사이트를 열 수 없으면 아래 잠정 토큰으로 시작하고 그 사실을 알려라.
- 잠정 디자인 토큰 (요구사항 정의서의 SAEHAN 로고·문서 색에서 추출, 사이트 확인 후 조정):
  - Primary(브랜드 네이비) `#091E7C`, Primary 진한 글자 `#14213D`, Accent 블루 `#2F5BEA`
  - 배경 `#FFFFFF` / 보조 배경 `#F3F6FD`, 테두리 `#E5E7EB`, 본문 글자 `#2B2F36`, 보조 글자 `#6B7280`
  - 상태색: 부족·위반 `#E5484D`, 경고(안전재고 미달) `#E0A21B`, 정상·입고 `#3D9A4A`
- 톤: 제조 기업답게 **차분하고 신뢰감 있는 B2B 업무 도구**. 장식보다 정보 밀도와 가독성 우선, 둥근 모서리 6~8px, 그림자는 최소화, 강조는 브랜드 네이비 한 가지로.
- 디자인 토큰은 CSS 변수(또는 Tailwind theme)로 한 곳에 모아, 사이트 확인 후 색만 바꾸면 전체가 바뀌게 한다.
- 화면 레이아웃은 요구사항 정의서 그림 4(계획 간트 화면 예시), 그림 5(씨벌크 원료 화면 예시)를 참고한다.

### 4. 계산 규칙 (요구사항 5장, 반드시 이대로)
```
예상 생산량(호기, 일) = 일일 Capa × 교체 가동률 계수(교체일만) × 주말 계수(토·일만)
                         가동 불가일이면 0
예상 재고(제품, 일)   = 전일 재고 + 그날 해당 제품 예상 생산량 합계 − 출고계획량
씨벌크 사용량(일)     = Σ(사출 설비 계획 수량 × 제품(프리폼) 중량)
사일로 재고(일)       = 전일 재고 + 입고 − 씨벌크 사용량
```
- 셀에 계획 수량을 직접 입력했으면 그 값을 쓰고, 비어 있으면 예상 생산량을 쓴다.
- 교체 손실 계수 기본값(기준정보에서 수정 가능): PET1(1-Stage) B/M 교체 3시간·0.87, Full set은 익일 가동(교체일 0), PET2 B/M 2시간·0.91, PET2 Full set 4시간·0.83, PE 6시간·0.75.
- 예상 재고 < 안전재고 → "경고", 예상 재고 < 0 → "부족". 부족이 처음 생기는 날짜와 수량을 제품별로 낸다.
- 제약 위반: ① 호기 허용 목록 밖의 금형, ② 하루 금형 교체 횟수 초과, ③ 가동 불가일에 배치.
- 사일로: 55m³(최대 약 40톤), 150m³(최대 약 120톤), 합계 상한 160톤. 하한은 설정값. 1~2주는 계획 기반, 3~6주는 "월별 운용안 물량 ÷ 가동일수"로 추정한다. 발주 리드타임 기본 30일, 1회 입고 22~23톤.
- 발주 추천: 하한 미달이 처음 예상되는 날짜에서 리드타임을 빼서 발주 기한을 계산하고, 하한 위로 회복하는 데 필요한 물량을 입고 단위(22톤)로 올림해 제안한다. 근거(미달 예상일, 일평균 사용량)를 같이 반환한다.
- **모든 계산은 순수 함수로 분리한 `lib/engine` 모듈**에 두고, 셀마다 계산 근거(Capa, 적용 계수, 결과)를 반환해 화면에서 펼쳐 볼 수 있게 한다(NFR-04).

### 5. 아직 확정되지 않은 값 (요구사항 9장)
아래는 고객 답변 전이므로 **하드코딩하지 말고 설정값(기준정보 화면에서 수정 가능)**으로 두고, 기본값과 함께 `docs/OPEN_QUESTIONS.md`에 정리해라.
- Q1 현행 계획표 사출기 행 숫자의 의미 → 엑셀 가져오기 시 무시하고 경고만 남김
- Q2 사일로 하한 → 기본 30톤
- Q3 Capa·수량 단위(본/천본) → 기준정보에 단위 필드, 기본 "본"
- Q4 하루 금형 교체 가능 횟수 → 공장 단위 기본 3회
- Q5 주말 계수 → 기본 0.8
- Q9 계획 대상이 아닌 사출 설비(A1, 2공장 P1~4)의 원료 사용량 → 일별 고정 기준값 입력 칸
- Q12 제품별 안전재고 → 제품 기준정보 필드, 기본 0

### 6. 샘플 데이터
- `data/samples/`에 실제 자료가 있으면 그것을 쓴다. **실제 자료는 git에 커밋하지 않는다**(`.gitignore` 처리).
- 없으면 `scripts/make-fake-data.ts`로 **가상 데이터**를 만들어 Supabase 시드(`supabase/seed.sql` 또는 시드 스크립트)로 넣는다: PET 1~18호기, 제품 30~40개, 호기별 허용 금형 3~6개, 15일 계획, 출고일정, 공장 재고, 사일로 기초재고·입고 일정. 현행 엑셀 계획표 형식(시트별, B열 허용 금형, 날짜 셀에 제품명 텍스트, 일부 셀에만 수량)을 흉내 낸 `.xlsx`도 만들어 FR-03 가져오기를 시험한다.

### 7. 진행 순서 (마일스톤마다 멈추고 결과를 보고해라)
1. **계획 제안:** 요구사항을 읽고 폴더 구조, 데이터 모델(ERD, Supabase 테이블·RLS 정책), API 목록, 화면 목록, 디자인 토큰(splatech 사이트 확인 결과), 마일스톤별 완료 기준을 제안한다. 요구사항에서 모호한 점은 질문 목록으로 낸다. **내 승인 전에는 코드를 쓰지 마라.**
2. **M1 데이터·계산 엔진:** Supabase 스키마·마이그레이션, 가상 데이터 시드, `lib/engine`(예상 생산량, 수급, 제약, 사일로, 발주 추천)과 Vitest. Next.js 기본 화면을 Vercel 프리뷰에 한 번 배포해 연결을 확인한다. 5장 예시(일일 Capa 100,000본 + B/M 교체 → 87,000본)를 테스트 케이스로 넣는다.
3. **M2 엑셀 입출력:** 기준정보(운용안) 일괄 등록, 현행 계획표 가져오기(FR-03, 매칭 실패 셀 목록), 현행 양식 내보내기(FR-12), 출고일정표·수불 업로드(FR-05).
4. **M3 계획 간트 화면(6.1):** 호기 × 15일 간트, 드래그 이동·연장, 즉시 재계산(1초 이내), 제약 위반 빨간 테두리, 오른쪽 경고 목록, Rev 저장과 변경 사유 필수(FR-04), Rev 비교.
5. **M4 수급 검증(6.2)과 씨벌크 원료(6.3) 화면:** 부족·경고·과잉 색 구분, 우선순위 가중치 정렬(FR-11), 사일로 6주 그래프·상하한선·발주 추천 카드, 입고 일정 등록.
6. **M5 기준정보·조회(6.4)와 마무리:** 기준정보 편집, Rev 이력, 조회 전용 권한(Supabase Auth + RLS로 작성/조회/관리 3역할), Vercel 프로덕션 배포, README(로컬 실행, 환경변수, Vercel·Supabase 설정, 백업, 사내 호스팅 이전 방법), 운영 매뉴얼 초안.

### 8. 작업 규칙
- 요구사항 ID(FR-xx, NFR-xx)를 커밋 메시지, 코드 주석(필요할 때만), 테스트 이름에 붙여 추적할 수 있게 해라.
- 요구사항과 다르게 구현해야 할 이유가 생기면 임의로 바꾸지 말고 먼저 알려라.
- 마일스톤마다 Vercel 프리뷰 URL을 함께 보고해라.
- 각 마일스톤 끝에 ① 무엇을 만들었는지 ② 테스트 결과 ③ 실행 방법 ④ 요구사항 대비 남은 것 을 짧게 보고해라.
